# Doppelimplementierungen: TemplatesBrowser vs. ProjectsBrowser → Kandidaten für FolderBrowser

Nur Kandidaten, bei denen **beide** Browser gleichartig reagieren (gleiches Muster, unterschiedliche Variablen/Callbacks). Ziel: Logik einmal im gemeinsamen Parent FolderBrowser oder über einheitliche Callbacks abbilden.

---

## 1. Signal-Handler (main.qml)

| # | Signal / Bereich | TemplatesBrowser (main.qml) | ProjectsBrowser (main.qml) | Gleichartig? | Kandidat für FolderBrowser? |
|---|------------------|-----------------------------|----------------------------|--------------|-----------------------------|
| 1 | **onClipboardRequested** | `openClipboard()` | `openClipboard()` | **Identisch** | ✅ Ja – einmaliger Host-Callback z.B. `onClipboardRequested: openClipboard`; FB könnte optionalen Callback aufrufen, oder Verbindung in main nur 1x (wenn beide gleiche Aktion wollen). |
| 2 | **onClipboardDropRequested** | `dropToClipboard(payload)` | `dropToClipboard(payload)` | **Identisch** | ✅ Ja – wie oben, ein Callback(payload) vom Host. |
| 3 | **onFolderPreviewed** | `previewCTD(resolveTemplateDisplayPathToReal(path))` | `previewCTD(path)` | Gleiche Aktion, Templates resolvet Pfad | ✅ Ja – FB emittiert weiter `folderPreviewed(path)`; Host bekommt einen Callback z.B. `onPreviewPath(path)` und wendet ggf. Resolve an, dann `previewCTD(realPath)`. Einheit: „Preview für diesen (Anzeige-)Pfad“. |
| 4 | **onMoveEntryRequested** | `moveEntry(sourcePath, resolve...(targetDir))` | `moveEntry(sourcePath, targetDir)` | Gleiche Aktion, Templates resolvet Ziel | ✅ Ja – Host-Callback `onMoveEntry(sourcePath, targetDir)`; Host resolvet bei Templates vor dem Aufruf. Einheit im FB: nur Signal; Resolve-Logik bleibt in main. |
| 5 | **onCreateFolderRequested** | `requestCreateFolderAt(resolve...(basePath))` | `requestCreateFolderAt(basePath \|\| cwp)` | Beide rufen requestCreateFolderAt mit Zielpfad | ✅ Ja – Host-Callback `onCreateFolderRequested(basePath)`; Host macht Resolve/Fallback und ruft `requestCreateFolderAt(realPath)` einmal. |
| 6 | **onStyleChanged** | `level2ButtonStyle = style` | `folderItemStyle = style` | Nur andere Variable setzen | ✅ Ja – FB behält Signal; main könnte einen gemeinsamen Handler nutzen, der eine window-Property setzt, und beide Browser binden daran – oder FB bietet optionalen Callback(style) für „Style übernommen“. |
| 7 | **onToggleMode** | `level2VerticalView = !level2VerticalView` | `verticalProjectView = !verticalProjectView` | Nur andere Variable togglen | ⚠️ Teilweise – gleiches Muster (Toggle einer View-Variable); Aufnahme in FB nur als optionaler Callback (FB kennt die konkrete Variable nicht). |
| 8 | **onToggleSearch** | `level2SearchActive = !level2SearchActive` | `window.searchActive = !window.searchActive` | Nur andere Variable togglen | ⚠️ Teilweise – wie onToggleMode. |
| 9 | **onToggleEmbryos** | Toggle + `listTemplates(listingPath)` + `updateStandardFolders()` | Toggle + `updateSubProjects()` | Toggle + unterschiedlicher Refresh | ⚠️ Teilweise – gleiches Muster „Toggle + Refresh“, Refresh-Logik unterschiedlich; nur als Callback abbildbar. |
| 10 | **onSearchTextChanged** | `level2SearchText = templatesBrowser.searchText` | `window.searchText = ...; updateSubProjects()` | Rückbindung + ggf. Update | ⚠️ Teilweise – Rückbindung in Host-Variable + optionaler Seiteneffekt; schwer komplett in FB zu ziehen. |
| 11 | **onSearchTextEdited** | `level2SearchText = value; updateStandardFolders()` | `window.searchText = value; updateSubProjects()` | Setzen + Refresh | ⚠️ Teilweise – einheitlich: „Text gesetzt + Refresh“; Refresh-Methode unterschiedlich → Host-Callback(value). |

## 2. Optionale Callbacks (Properties) in FolderBrowser

Wenn FB **optionale** Funktionen anbietet, kann main diese einmal setzen und beide Browser durch dieselbe Logik bedienen (wo sinnvoll).

| # | Vorschlag | Aktuell (doppelt in main) | Einordnung |
|---|-----------|----------------------------|------------|
| A | **resolvePathForHost(path)** | Templates: `resolveTemplateDisplayPathToReal(path)`; Projects: path unverändert | FB könnte `property var resolvePath: function(p) { return p }` haben; main setzt bei Templates `resolvePath: resolveTemplateDisplayPathToReal`. Dann nutzen alle „Pfad an Host zurückmelden“-Signale diesen Resolver. |
| B | **onPreviewRequested(path)** | onFolderPreviewed → previewCTD(resolve(path)) vs. previewCTD(path) | Ein Callback; FB ruft ihn mit Anzeige-Pfad, Host wendet Resolve an und ruft previewCTD. |
| C | **onMoveRequested(source, targetDir)** | wie onMoveEntryRequested oben | Bereits reines Signal; Einheit durch einen gemeinsamen main-Handler mit Resolve-Option möglich. |
| D | **onCreateFolderRequested(basePath)** | wie oben | Ein Callback; Host resolvet und ruft requestCreateFolderAt. |

## 5. Kurzfassung: stärkste Kandidaten

| Priorität | Kandidat | Aktion |
|-----------|----------|--------|
| **Hoch** | **onClipboardRequested / onClipboardDropRequested** | Identische Handler → in main nur 1x verbinden (beide Browser gleiche Aktion) oder FB ruft einen optionalen Callback. |
| **Hoch** | **projectIconFunction / pathColorFunction** | Fast identischer Code → Default-Implementierung in FolderBrowser (mit backend/theme-Optionen), main setzt nur bei Abweichung. |
| **Mittel** | **onFolderPreviewed / onMoveEntryRequested / onCreateFolderRequested** | Einheitliches Muster „Pfad/Callback“; Host resolvet bei Templates. Ein Callback pro Aktion, FB nur Signal; main ein Handler mit Resolve-Logik pro Browser oder ein Resolver pro Instanz. |
| **Mittel** | **onStyleChanged / onToggleMode / onToggleSearch** | Gleiches Muster (Variable setzen/togglen); Aufnahme in FB nur als optionaler Callback(style) bzw. Toggle-Callback. |
| **Niedrig** | **onToggleEmbryos / onSearchTextEdited** | Muster „Aktion + Refresh“; Refresh unterschiedlich → nur als Callback abbildbar. |
